# Money-system findings (running report)

Discovered while implementing the money-system plan. Each entry: what, where, why it matters, what needs doing.
No production data has been changed for any of these.

| # | Finding | Where | Why it matters | Needed |
|---|---------|-------|----------------|--------|
| 1 | Payment deletion hard-deletes the receipt and its allocations | `app/api/admin/invoices/actions/route.ts` `delete_payment_batch` | Original financial event is erased; `paid_amount` is left unchanged, so balance and allocations diverge (it only returns a "mismatch" warning) | Replace with void/reverse (migration `20261002000000`) |
| 2 | `record_payment` accepts a raw `payload` and writes it straight to `invoices` | same file, `record_payment` fallback branch | Any field, including `paid_amount`/`total_amount`/status, can be changed with no event | Remove or whitelist the branch; log before/after |
| 3 | `update_status` writes `locked_late_fee_amount` (freeze/unfreeze) and triggers fee billing and points sync | same file, `update_status` | Status change has monetary side effects, against the plan's rule 1 | Make status change write status only |
| 4 | `delete_many` hard-deletes invoices | same file, `delete_many` | Invoice with allocations/history can vanish without an adjustment event | Block when money exists, or require cancel + reason |
| 5 | `money_events` helper existed untracked with no table and no callers | `lib/money-events.ts` | Audit log silently failing | Table added in migration `20261002000000`; callers being wired |
| 6 | Reconciliation has only invoice-level checks | `lib/reconciliation.ts` | Plan Phase 8 needs batch/allocation/credit/refund/points checks | Extend, then add admin review view |
| 7 | Invoice UI "cancel payment entry" edited `paid_amount`, history and status directly from the browser's computed values, and recomputed status as `paid` when `paid >= total` | `lib/hooks/use-invoices-state.ts` `cancelPaymentEntry` | Bypassed allocations/receipts entirely; legacy history entries with no `payment_batch_id` can no longer be cancelled automatically | Rerouted to `void_payment`; legacy entries need a manual adjustment path (Phase 3 adjustments) |
| 8 | Local `.env.local` points at the PRODUCTION Supabase project | `.env.local` | Running the dev server or any script locally writes to real data | Create a separate test project and a separate env file for it |
| 9 | `supabase/migrations/final-schema.sql` is stale: it lacks `payment_batches` and many later tables/columns (points, slip_rejections, etc.), so a fresh database cannot be rebuilt from the repo alone | `supabase/migrations/` | No reproducible way to build a test/new environment; the real production schema is only in production | Export the production schema (read-only `supabase db dump --schema-only`) into the repo |
| 10 | `tenant_credits` has a required `bucket` column (deposit/advance/unapplied); every writer must set it or balances cannot be grouped | `20261002000200_migration-tenant-credits.sql` | Wrong/missing bucket silently misstates held deposit vs advance rent | Single writer function that sets bucket |
| 11 | `refund_due_vs_paid` ignores `refunded` credit rows; payouts are the source of truth for money sent | `20261002000300_migration-refund-payouts.sql` | Recording a refund in both places would subtract it twice | Pick one convention; writer must never do both. Also confirm advance rent is non-refundable |
| 12 | `adjustments` rows do not yet change invoice totals | `lib/invoice-total.ts` | An adjustment could be recorded without changing what the tenant owes | Add a required adjustments term to `computeInvoiceTotal` before any writer uses the table |
| 13 | No FKs or cross-row checks on adjustments/credits: reversal target, sign and invoice are not validated | new migrations | Bad reversal rows can be inserted | Enforce in the single writer function (app or SQL) |
| 14 | Late-fee unique key is (source invoice, period, policy version): a period cannot be re-posted even if the first target invoice was cancelled | `20261002000400_migration-late-fee-charges.sql` | Cancelled target leaves the fee stuck | Correct with a waiver adjustment or a new policy version |
| 15 | Views were not `security_invoker` (could bypass RLS if exposed via PostgREST) | tenant_credit_balances, refund_due_vs_paid | Data exposure through the API | Fixed in files; re-apply to test project |
| 16 | Reconciliation check column names are assumed (carry_forwards.amount, money_events.invoice_id, payment_history.payment_batch_id) | `lib/money/reconciliation-checks.ts` | Wrong names give false negatives | Confirm against the real production schema |
| 17 | Carry-forward "exceeds outstanding" check can false-positive once a source is paid via the chain; check 7 cannot see total-only edits without old/new values in money_events | `lib/money/reconciliation-checks.ts` | Noise or missed edits | Refine once real data is available |
| 18 | First reconciliation run will show many high findings from pre-ledger invoices with paid_amount and no allocations | production data | Expected noise, not new breakage | Categorise as "legacy, no receipt record" in the report |
| 19 | `lib/reconciliation.ts` uses a different finding shape from the new checks | `lib/reconciliation.ts` | Two reconciliation systems | Unify when the admin review view is built |
| 20 | `redeemPoints` is not atomic: updates invoice, then inserts the ledger row, then tries to revert the invoice if the insert fails; a crash between leaves a discount with no points spent or vice versa | `lib/points-ledger.ts` ~569-690 | Points and discount can diverge | One DB function writing both sides with a shared key (planner: `lib/money/points-redemption.ts`) |
| 21 | Redemption idempotency key is optional and only checked against `point_ledger_entries`; a retry without a key redeems twice | `lib/points-ledger.ts` | Double redemption | Require the key; unique index across both writes |
| 22 | `deleteRedemption` hard-deletes: points return but the invoice discount stays, and the monthly redemption limit resets | `lib/points-ledger.ts` ~811 | History destroyed, balances diverge | Replace with paired reversal rows |
| 23 | Discount cap uses `total_amount - paid_amount`, so late fees and carried debt can be discounted; the rent/utility target never limits the amount | `clampRedemptionBaht` | Discount on charges that should not be discountable | Pass only rent + utilities remaining as redeemable charge |
| 24 | `redeemPoints` writes `total_amount`/`discount_amount` directly, bypassing `lib/invoice-total.ts` | `lib/points-ledger.ts` | A later recompute that omits the discount erases it silently | Route through the engine's discount term |
| 25 | Balance and monthly-limit checks are read-then-write with no locking | `lib/points-ledger.ts` | Concurrent requests can overdraw points or exceed the limit | Do the checks inside the same DB function as the writes |
